## JSON structure and key names

Use stable, meaningful keys in English, with PascalCase sections and keys:

- `Main.ArrivedPeople`
- `Main.SearchPlaceholder`
- `Nav.Dashboard`
- `Admin.Guests.Relationship`
- `Admin.Tables.AddTable`
- `Common.NextPage`

The key identifies the meaning, and its value is the translated text. Do not use the actual Chinese sentence as the key. Avoid keys with spaces or punctuation such as `"Arrive People ."`.

## Initialization method

- Import `CN.json` and `EN.json` directly through Vite. Do not add a network translation loader or language-detector package for two bundled languages.
- Register `initReactI18next` once in `src/i18n/index.ts`.
- Map the `CN.json` resource to the standard language code `zh-CN`, and `EN.json` to `en`. The filenames are CN/EN; the runtime language codes are not `CN`/`EN`.
- Use one default i18next namespace, `translation`, containing the nested sections shown above. `Main` is an object inside that namespace, not a separate resource file.
- Restore a supported saved preference from `localStorage` key `wedding-language`. If no valid preference exists, default to `zh-CN`.
- Set a Chinese fallback and restrict supported languages to `zh-CN` and `en`. Handle an invalid saved value safely.
- Initialize bundled resources before rendering the application, using initialization supported by the installed i18next version. Avoid a first-frame flash of raw translation keys or the wrong language.
- Update `document.documentElement.lang` and the document title when the language changes.
- Catch language-preference storage failures so they do not prevent the app from opening.
- Do not write the language into `wedding-react-v2`, auth state, guest records, or URLs.
- If TypeScript needs JSON module resolution enabled, make only the necessary compiler configuration change. Add typed resource-key augmentation without weakening the existing compiler checks.

## Component usage

Components use `useTranslation()` so changing the language rerenders the existing interface immediately:

```tsx
import { useTranslation } from 'react-i18next';

export function AttendanceExample({ arrived, total }: { arrived: number; total: number }) {
  const { t } = useTranslation();

  return (
    <div>
      <span>{t('Main.ArrivedPeople')}</span>
      <strong>{t('Main.ArrivalSummary', { arrived, count: total })}</strong>
    </div>
  );
}
```

Use interpolation for names, counts, table numbers and other changing values. Do not build translated sentences by concatenating fragments in Chinese word order. Use i18next plural forms where English singular/plural differs; both files can include `_one` and `_other` keys so their resource structures match.

Keep stable translation keys in module-level tab definitions or configuration, then translate them during render. Do not call `t()` once at module load and freeze the resulting labels.

## Notifications and errors

- Keep pure API/storage modules independent of React hooks. Do not call `useTranslation` inside an API module or ordinary utility.
- Represent known business/storage/migration errors with stable error codes or translation keys and parameters. Translate them at the UI boundary.
- Store translation keys and parameters for active notifications/errors rather than persisting already translated sentences in component state. An open notice or recovery screen should follow a language change.
- Keep unknown technical error details for diagnostics and show a translated generic error to users.
- Confirmation dialogs must use the current language when opened. Preserve deletion and import confirmation behavior.
- Do not put user-entered content into HTML translation strings. Keep normal React escaping; avoid `dangerouslySetInnerHTML`.
